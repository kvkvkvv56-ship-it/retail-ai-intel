# 行业与竞对 AI 洞察情报站 · 技术方案

> 技术参考：架构、各阶段的规则、数据模型、API 契约。
> **为什么这么设计**见 [`方法论.md`](方法论.md)，**怎么跑起来**见 [`运行说明.md`](运行说明.md)。
> 本文只写这两者不覆盖的部分，不重复论证。

## 1 · 评分对齐

每个模块都要能指回评分表，否则不做。

| 维度 | 分值 | 对应设计 |
|---|---|---|
| 信息质量与覆盖 | 25 | 五类信源分层、六通道采集、信源健康度自检 |
| 核验严谨性 | 25 | 拒绝台账、分类型核验路径、五级置信度、三级时间口径、claims 结构约束 |
| 洞察深度 | 25 | 阶段打折、状态判定、事件关系边、周报合成 |
| 可复用性 | 25 | 配置驱动的提示词、数据集切换、mock 复现、方法论文档 |

「展示一次完整运行结果，包括原始信息明细、分类核验过程和洞察输出」
→ 由首页「运行回放」一屏满足。

## 2 · 架构

### 2.1 谁在什么地方跑

流水线跑在 GitHub Actions 上，不在开发者的机器上。开发者电脑只用于开发和
人工复核，随时可离线，不在关键路径上。

```
开发者电脑     开发 + 人工复核 CLI（可离线，不影响线上）
    │  git push / pull
    ▼
GitHub 仓库    数据真相源（JSONL）+ API 快照 + 流水线代码
    │  定时触发（每日两轮）
    ▼
GitHub Actions 跑流水线 → 导出快照 → commit 回仓库     ← 真正的「服务器」
    │
    ├─ raw.githubusercontent  Worker 优先读（最新数据，不需重新部署）
    └─ Cloudflare ASSETS      读不到时兜底（部署时打包的版本）
                 └─ ai.kvkvkvv.site
```

### 2.2 数据流

```
生产侧（Python，跑在 Actions）
  S0 采集 → S1 去重 → S2 预筛 → S3 抽取 → S4 归并 → S5 核验 → S6 关系边 → S7 洞察
      │                                                                    │
      └──────────── intel.db（SQLite 运行时索引，gitignore）─────────────────┘
                              │ dump
                    data/*.jsonl（真相源，git 提交）
                              │ S8 导出
                    web/public/api/v1/*.json（API 快照，git 提交）

线上只读侧（Cloudflare Worker）
  静态资源 + REST API（读快照）+ SSE（定制简报三段式在线生成）

人工复核侧（本地 CLI，不上线）
  pull → rebuild → 复核 → dump → commit → push   留痕进 reviews.jsonl
```

### 2.3 存储：JSONL 是真相源，SQLite 是可重建的索引

| 文件 | 内容 | 提交？ |
|---|---|---|
| `data/*.jsonl` | items / events / claims / edges / rejects / runs / reviews / reports | ✅ 行级 diff |
| `data/llm_cache.jsonl` | LLM 调用缓存，键为 `sha1(model+messages)` | ✅ mock 复现需要 |
| `web/public/api/v1/` | API 快照，Worker 直接读 | ✅ 不提交则线上数据不更新 |
| `intel.db` | SQLite 查询索引 | ❌ `--rebuild` 五秒从 JSONL 重建 |

不提交 SQLite 的原因：二进制文件 git 存不了增量 diff，每次提交存一份完整副本。
JSONL 的额外收益是**在 GitHub 网页上直接可读**——点开 `data/items.jsonl`
就能看到每条的 URL、来源、双时间戳，这是「可追溯」最直接的证明。

### 2.4 为什么线上不挂数据库

| 理由 | 说明 |
|---|---|
| 可复用性 | 数据在云库里，复现者要先注册账号、建库、配 token；数据在仓库里，clone 完就能跑 |
| 没有写入需求 | 站点纯只读。人工复核走本地 CLI，定制简报即时生成不落库 |
| 不会挂 | 快照走边缘缓存，无连接池、无查询超时、无配额耗尽 |

### 2.5 技术栈

| 层 | 选择 | 理由 |
|---|---|---|
| 流水线 | Python 3.13，**仅标准库**（urllib / sqlite3 / json） | CI 无需 pip install，少一类失败 |
| 存储 | JSONL 真相源 + SQLite 可重建索引 | 见 2.3 |
| LLM | DeepSeek 分层（预筛便宜档 / 抽取与洞察强档） | 预筛吃掉最大调用量，必须便宜 |
| 检索 | Exa（news 类目） | 覆盖没有稳定订阅源的长尾 |
| 向量 | Jina embeddings v3（1024 维），int8 量化后进 JSONL 缓存 | 归并召回 + 线上语义检索，见 2.6 |
| 前端 | Vite + React，**单一实现** | v1 有 4 份并行实现，那是它的根本问题 |
| 部署 | Cloudflare Worker（ASSETS + API + SSE） | 无服务器，零运维 |
| CI | GitHub Actions **只跑 Python** | v1 被 `npm ci` 挂死拖垮过，前端已移出关键路径 |

> 没有 FTS5、没有向量数据库。前者被词面匹配替代；后者在千级数据上不必要——
> 114 条 × 1024 维的点积朴素扫描只要几十毫秒，引入 faiss/pgvector 只会抬高复现门槛。

### 2.6 向量的两处用途

向量落 `data/embeddings.jsonl`，键是 `sha1(model+task+text)`，重跑命中缓存不计费。
**int8 量化后 base64 存储**：1024 维 float 直接存 JSON 是 7KB/条，几百条就
4.5MB，git 扛不住；量化后 1.4KB/条，对余弦的精度损失可忽略。

1. **S4b 跨事件归并的召回**（见 3.4）——向量提候选，LLM 逐对裁决
2. **线上语义检索**——事件向量在导出时算好写进 `vectors.json`（114 条 156KB），
   线上只对用户 query 调一次接口，余弦在 Worker 里算。既不必挂向量库，
   也不必为检索多存一份数据。`JINA_API_KEY` 缺失时全部退回词面匹配

## 3 · 流水线各阶段

判定依据见 [`方法论.md`](方法论.md)，这里只给规则本身。

### S0 采集（六通道）

| 通道 | 说明 |
|---|---|
| `rss` | 原生 / 直连 RSS |
| `rsshub` | RSSHub 公共实例，多实例轮询，全部失败记入 `collect_errors` 不阻断 |
| `jina` | Jina Reader 抓列表页 → 标题级粗筛 → 只对命中的取全文 |
| `aihot` | AIHOT 日报作为发现渠道，落库一律回原文链接 |
| `direct` | 服务端渲染页面直抓，需配 `article_url_pattern` 排除导航链接 |
| `exa` | 语义检索，主体 × 领域的查询矩阵 |

> 通道归属是逐个实测出来的，不是按信源类型分配的。原计划 RSSHub 作主通道，
> 实测 5 个路由族里 4 个已失效；原计划若干官网可直抓，实测抓回来的是
> 「投资者关系」「文化与价值观」这类导航链接。

### S1 去重（三层 + 窗口 + 关键词粗筛）

```
L1  URL 规范化后精确匹配        → duplicate_url
L2  SimHash 汉明距离 ≤ 阈值     → syndication
L2a 标题归一化后精确匹配        → syndication
    （L2 的指纹含正文，不同站点模板差异会让同标题稿件指纹不同）
窗口 published_at 早于采集窗口  → stale（inferred 时间不参与硬判定）
粗筛 AI 词 × 行业词 双命中      → off_topic（零成本，在调 LLM 之前）
```

全部写进 `rejects` 台账，带拦截层与原因码。

### S2 预筛 · S3 抽取

- S2 便宜档，只判「是否与观察范围相关」，宁可放过不要错杀
- S3 强档，**提示词按信源一手性分流**：A 类只记官方口径且不打折，
  B/C 类正常抽取，D 类不抽事实只作归并证据，E 类禁止产出 fact
- S3 的阶段判断落 `items.draft_stage` 持久化——不能只留在内存，S5 是全库重算
- 提示词的公司 / 领域 / 阶段枚举全部从 config 读取，换行业不改代码

### S4 归并

按公司通读聚类。输出三层而不是二选一：

```
groups     确定同一件事           → 合并
suspects   拿不准                 → 标 suspect_duplicate 进人工队列
relations  不同事件但有关系        → follows / corroborates / contradicts / causes
```

两条兜底，都是「静默丢失」踩出来的：

- 模型分组未覆盖的候选，各自独立成事件（`orphan_rescued`）
- 某公司归并调用失败时，其候选逐条独立成事件（`merge_fallback`），
  不能留在 `extracted` 状态——那次事件数从 129 掉到 79，51 条凭空消失

### S4b 跨事件归并复核（向量召回 + LLM 裁决）

S4 按公司分组，同一事件被判成不同 company 就永远不会被放在一起比较。
S4b 补这个盲区。原实现把**全部事件**塞进一次调用整体通读，两个问题：
不可扩展，且实测漏判严重——事件涨到 133 个后，余弦最高的 8 对全是真重复
（其中一对标题只差一个引号），整表通读一对都没抓到。

改为向量召回：

```
两两余弦 ≥ 0.80  →  候选对（占全部组合约 1.1%）
                 →  分批送模型逐对裁决
                 →  duplicates 自动合并 / suspects 进人工队列
```

阈值是标定出来的：事件两两余弦中位 0.560、p99 0.807。这是**召回**阈值不是
判定阈值，判定由 LLM 做，所以宁可宽。实跑一次召回 97 对，合并 19 个重复事件、
39 对转人工，10 次调用 ¥0.09。向量不可用时退回整表通读，行为与改动前一致。

### S5 核验（纯规则，全库重算）

```python
# 置信度
官方确认·多源印证   has_A and n_org >= 2
官方一手           has_A
多源已验证                    n_org >= 2
深度单源           has_B
单源待确认         其余

# 独立组织数：按 org 去重；与事件主体存在 affiliated_with 关系的信源不计。
# 一律用 effective_class（归因后一手性），不用 source_class（采集载体）

# 落地阶段：取保守值，依据记入 stage_basis
stage = min(官方自述阶段, 第三方报道阶段)

# 状态：event_date（事情发生时间）优先于 first_seen_at（系统发现时间）
新增 / 延续 / 静默 / 旧闻·背景

# 复核态粘性：已裁决过的（watching/confirmed/rejected/suspect_duplicate）
# 不被重置回 pending
```

### S6 关系边 · S7 洞察

- S6 规则边 `same_actor_track`：同公司事件按时间排序，相邻两个连边
- S7 周报周期口径是**事件发生周**，不是「本轮采集到」——前者可回填历史
- S7 是 `recommendation` 的唯一产出点，必须带 `audience` 与
  `needs_internal_data`；模型编造的 EV 编号在落库前被剔除

### S8 导出

SQLite → `web/public/api/v1/*.json`，路径即 API 路径。
同时导出 `docs/*.md` 的文档快照与前端离线兜底数据。

### 阶段级容错

S2–S7 每个阶段都包了失败兜底：异常记入 `runs.stats.stage_errors` 并继续，
不让单点故障带走整轮已完成的工作。S5 是纯规则的全库重算，前面失败它照样跑。

## 4 · 数据模型

真相源是 `data/*.jsonl`，每张表一个同名文件，一行一条记录。SQLite 是运行时
索引。**权威定义在 `pipeline/store.py`**，下表是字段速览。

| 表 | 字段 |
|---|---|
| `sources` | id · name · **org**（去重单位）· source_class · domains · channel · channel_ref · **affiliated_with** · reliability · partial_content · active · note |
| `items` | id（`sha1(url_canonical)[:16]`）· url · url_canonical · title · content · **source_id**（采集载体）· source_class · **original_source**（原始出处）· **effective_class**（归因后一手性）· published_at · **time_source** · discovered_at · run_id · channel · simhash · status · event_id · **draft_stage** |
| `events` | id · event_key · title · summary · company · domains · **stage** · **stage_basis** · **confidence** · status · first_seen_at · last_update_at · **event_date** · independent_orgs · **review_state** |
| `claims` | id · event_id · **kind**（fact/inference/recommendation）· text · **source_item_id** · based_on · attributed_to · audience · needs_internal_data |
| `edges` | id · from_event · to_event · relation · basis · created_by（rule/llm/human） |
| `rejects` | id · run_id · item_id · url · title · source_name · **stage**（拦截层）· **reason_code** · reason_detail · merged_into · created_at |
| `runs` | id（`RUN-YYYYMMDD-HHMM`）· started_at · finished_at · mode · dataset · **stats**（各阶段计数 JSON）· cost · **config_hash**（配置指纹，证明可复现） |
| `reviews` | id · target_type · target_id · action · note · reviewer · created_at |
| `reports` | id（`W-YYYY-MM-DD`）· period_start · period_end · headline · body（JSON）· generated_at · run_id |

三条程序层约束（不是提示词约束）：

- `claims.kind='fact'` 必须有 `source_item_id`，且不得来自 D/E 类
- `claims.kind='recommendation'` 必须**没有** `source_item_id`
- `items.effective_class` 是核验的唯一依据，`source_class` 只记载体

新增字段要同时改三处：`SCHEMA` 建表语句、`TABLES` 列清单（决定 dump/rebuild
范围）、`Store._migrate()`——`CREATE TABLE IF NOT EXISTS` 不会给已存在的表补列。

## 5 · API 契约

```
GET  /api/v1/meta                 配置 + 各表计数 + 最近一轮 run id

GET  /api/v1/reports              周报列表

GET  /api/v1/sources              信源注册表 + 命中统计
GET  /api/v1/reviews              人工复核记录（按操作聚合）
GET  /api/v1/docs                 文档索引
GET  /api/v1/docs/:id             单篇文档（markdown + 目录）

```

错误统一 Problem JSON：`{type, title, status, detail, requestId}`。

## 6 · 前端

单一 React 实现。设计取向是**过程即产品**：首页不是事件列表，是运行回放。

| 视图 | 承担的评分点 |
|---|---|
| 运行回放 | 「展示一次完整运行结果」——漏斗五格每格可下钻到拒绝台账 |
| 事件库 | 可筛可查，详情页展示事实/推断/建议三分与全部信源 |
| 周报 | 关键发现锚定 EV 编号可点进核对；往期侧栏 + 全部周报页 |
| 定制简报 | 三段式在线生成，知识库材料与互联网材料分区标注 |
| 信源 | 按一手性分组列出，回应「信息源是否多元」 |
| 文档 | `docs/*.md` 渲染成开发者文档，评委不必 clone 仓库 |

三处交互细节：

- 简报输入框三态——静止时液态金属环、生成中 border beam、结束后普通线条框
- 思考过程用 thinking-orbs，状态按流水线阶段语义映射，不是随便转的动画
- 文档页正文与顶栏等宽（912px）居中，章节栏与目录栏用两侧留白铺到屏幕边缘；
  ≤780px 时顶部导航、周报往期、文档章节统一折叠成「当前项 + 点开选择」，
  不用横向滚动条——横滚看不全，也不知道自己在第几项

## 7 · 可复用性

换行业只改两个 JSON：`config/<dataset>.json`（观察主体、领域、检索矩阵、
关键词、窗口）与 `config/sources.<dataset>.json`（信源注册表与通道）。

关键是**提示词配置驱动**：`prompts.py` 里的公司 / 领域 / 阶段枚举全部从
config 读取。早先这些硬编码在提示词里，往 config 加主体不影响 LLM 阶段，
「换行业只改配置」是句空话。

`--mock` 用 `data/mock_llm/` 的固定回放替换全部 LLM 调用，零模型成本跑通全链路。

## 8 · 风险与缓解

| 风险 | 缓解 |
|---|---|
| RSSHub 公共实例不稳定 | 多实例轮询，全失败记入 `collect_errors` 不阻断 |
| 模型 429 / 网络抖动 | 阶段级容错，失败记账并继续；条目留在队列下轮重试 |
| GitHub schedule 延迟或丢弃 | 每个正式档挂两条补位 cron，距上次不足 6 小时则跳过 |
| Exa 额度耗尽 | 晚场 `--no-exa` 只跑免费通道；关键词粗筛在 LLM 之前拦掉八成 |
| 单源事件占比高 | 不隐藏，标「待确认」并进人工复核队列 |
| 付费墙 | 只取标题与导语，标 `partial_content`，不绕过 |

## 9 · v1 的教训

重做而不是继续改，原因集中在三条：

1. **4 份并行的前端实现**，改一处要同步四处，最后没人知道哪份是真的
2. **CI 关键路径上挂着 npm**，`npm ci` 挂死 44 分钟烧满作业超时，数据几天不更新
3. **严谨性写在提示词里**，「注意区分事实和推测」这类要求无法验证也无法回归

v2 的三条对应：单一前端实现；CI 只跑 Python；可判定的判断全部下沉成规则。
