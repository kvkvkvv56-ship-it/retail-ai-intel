# 行业与竞对 AI 洞察助手 · 技术方案

> 本文是重构版（v2）的完整技术设计，是后续 2–3 周开发的唯一依据。
> 上一版（v1）的经验教训见 §12。

---

## 0 · 设计原则

整个方案围绕一句话：**严谨性必须由数据结构保证，而不是由提示词祈祷。**

具体表现为三条铁律，贯穿全文：

1. **不丢弃，只降级并记账** —— 被淘汰的信息全部留痕，因为「识别出旧闻/转载」本身是交付物，悄悄丢掉等于没做。
2. **可信度由规则裁决，模型只做抽取** —— 置信度、阶段、状态全部是确定性规则算出来的，可回归、可审计。模型不参与可信度判断。
3. **过程即产品** —— 主界面展示的是"怎么得出的"，不是"得出了什么"。

## 2 · 系统架构

### 2.0 部署拓扑：谁在什么地方跑

**流水线跑在 GitHub Actions 上，不在开发者的机器上。** 开发者的电脑只用于开发和人工复核，随时可离线，不在关键路径上。

```
开发者电脑        开发 + 人工复核 CLI。可离线，不影响线上运行
     │
     │ git push / pull
     ▼
GitHub 仓库       数据真相源（JSONL）+ 流水线代码
     │
     │ 定时触发（每日 08:30 / 20:30）
     ▼
GitHub Actions    跑流水线 → 写回数据 → commit → 触发部署    ← 真正的"服务器"
     │
     │ 构建 + wrangler deploy
     ▼
Cloudflare        静态站 + API（读构建时打包进去的数据快照）
```

### 2.1 数据流

```
┌─────────────────── 生产侧（Python，跑在 GitHub Actions）──────────────────────┐
│                                                                              │
│  三通道采集 ──→ 去重 ──→ 预筛 ──→ 抽取 ──→ 归并 ──→ 核验 ──→ 关系边 ──→ 洞察  │
│   (S0)        (S1)    (S2)    (S3)    (S4)    (S5)    (S6)      (S7)        │
│      │                                                                │      │
│      └────────── intel.db（SQLite，运行时索引，不提交）──────────────────┘      │
│                                    │                                         │
│                    dump → data/*.jsonl（真相源，git 提交）                     │
│                                    │                                         │
│                          导出前端 JSON 快照 (S8)                              │
└────────────────────────────────────┼─────────────────────────────────────────┘
                                     │  git commit + push
┌────────────────────────────────────▼─────────────────────────────────────────┐
│  线上只读侧（Cloudflare Worker）                                              │
│    静态资源（React 构建产物） + REST API（读 JSON 快照） + SSE（定制简报）      │
└──────────────────────────────────────────────────────────────────────────────┘

┌──────────────────────────────────────────────────────────────────────────────┐
│  人工复核侧（本地 CLI，不上线）                                                │
│    pull → rebuild → 复核 → dump → commit → push                              │
│    信源分级维护 · 待确认队列裁决 · 归并纠错   →   留痕进 reviews.jsonl          │
└──────────────────────────────────────────────────────────────────────────────┘
```

### 2.2 存储：JSONL 是真相源，SQLite 是可重建的索引

| 文件 | 内容 | 是否提交 |
|---|---|---|
| `data/*.jsonl` | items / events / claims / edges / rejects / runs / reviews / reports | ✅ 提交。行级 diff，每轮只新增几十行 |
| `data/embeddings.jsonl` | 向量缓存（append-only） | ✅ 提交。mock 复现需要 |
| `intel.db` | SQLite 查询索引 + FTS5 | ❌ gitignore。`python -m pipeline rebuild` 5 秒从 JSONL 重建 |

**为什么不直接提交 SQLite 文件**：SQLite 是二进制，git 无法存增量 diff，每次提交存一份完整副本。一天 2 轮 × 3 周 ≈ 40 次提交，DB 涨到 10MB 就是几百 MB 的仓库。JSONL 全程只有几 MB。

**三个收益**：
1. 仓库轻，`git diff` 可读，能看出每轮到底新增了什么
2. "可 SQL 查询"这个可追溯性证据不丢——任何人一条命令就有个能查的 SQLite
3. **JSONL 在 GitHub 网页上直接可读**。评委点开 `data/items.jsonl` 就能看到每条的 URL、来源、双时间戳——这是"可追溯"最直接的证明，比任何界面都硬

### 2.3 为什么线上不挂数据库

| 理由 | 说明 |
|---|---|
| **可复用性直接扣分** | 25 分项要求"他人可按说明独立复用"。数据在 D1/Supabase 里，复现者必须先注册云账号、建库、配 token；数据在仓库里，`git clone` 完就能跑 |
| **线上没有写入需求** | 站点纯只读——评委只看不改。人工复核走本地 CLI，定制简报即时生成不落库 |
| **快照不会挂** | 数据打包进构建产物，边缘缓存直接吐。无连接池、无查询超时、无配额耗尽 |

### 2.4 技术栈

| 层 | 选择 | 理由 |
|---|---|---|
| 流水线 | Python 3.12，标准库 + httpx | v1 的零依赖策略在 CI 里 3/3 成功，保留 |
| 存储 | JSONL（真相源）+ SQLite/FTS5（可重建索引） | 见 §2.2 |
| 向量检索 | numpy 暴力余弦 | 千级数据不需要向量库 |
| Embedding | 智谱 embedding-3 / 通义 text-embedding-v3 | DeepSeek 无 embedding 接口；向量结果缓存入库，mock 模式零成本 |
| LLM | DeepSeek 分层（预筛便宜档 / 抽取洞察强档） | 抄 AIHOT 的成本工程 |
| 搜索 | Exa（news 类目） | v1 已验证，$0.1/轮 |
| 前端 | Vite + React，**单一实现** | v1 有 4 份并行实现，这是它的根本问题 |
| 部署 | Cloudflare Worker（assets + API + SSE） | v1 已跑通，保留 |
| CI | GitHub Actions **只跑 Python** | v1 的 npm ci 挂死从关键路径上摘除 |

## 3 · 信源体系

### 3.1 分层轴：一手性，不是发布主体身份

v1 用 `T1=官方 / T2=媒体 / T3=聚合` 分层，这个轴是错的——它会把晚点的独家报道判成 T2，把公司的 AI 公关稿判成 T1 最高权重。正确的轴是**这条信息离事件现场有多近**：

| 类 | 定义 | 典型信源 |
|---|---|---|
| **A · 当事方直述** | 主体自己说的 | 官方公众号、公告、财报/电话会、规则中心、招聘 JD、App 更新日志 |
| **B · 原创深度报道** | 有独立采访 / 内部信源 / 调查 | 晚点 LatePost、财新、36氪·智能涌现、字母榜、第一财经调查、光子星球 |
| **C · 常规媒体报道** | 基于公开信息的日常报道、快讯 | 亿邦动力、网经社、界面、虎嗅、新浪财经、量子位 |
| **D · 聚合转载** | 无增量信息的搬运 | 搜狐、今日头条、门户转载、通稿链 |
| **E · 观点评论** | 个人判断与分析 | 数字生命卡兹克、42章经、乱翻书 |

**A 和 B 都是一手**，只是一手的两种形态。B 类的情报密度通常高于 A 类——官方公告只说"我们宣布了什么"，独家报道能说"谁在推、投了多少人、内部怎么权衡的"。

### 3.2 分类型核验路径

核验机制主要是为 B/C/D 类存在的。A 类不需要多源交叉（当事方说的就是当事方说的），但需要另一套约束。

| 信源类 | 旧闻检测 | 转载归并 | 多源交叉 | 得到的置信度 | 允许抽取 |
|---|---|---|---|---|---|
| **A 当事方** | 需要 | 不适用 | **不需要** | 官方一手 | fact（"X 宣布了 Y"）<br>stage 须打折（§6.2） |
| **B 深度原创** | 需要 | 需要 | **不强制** | 深度单源 | fact + inference，须分离 |
| **C 常规报道** | 需要 | 需要 | **必须** | 多源已验证 / 单源待确认 | fact 为主 |
| **D 聚合转载** | 需要 | **主要处理对象** | 不计独立源 | 不单独成事件 | ❌ 不抽 fact，只做归并证据 |
| **E 观点评论** | 需要 | 需要 | 不适用 | 观点 | ❌ 不抽 fact，只抽 inference |

**两个必须注意的点：**

- **A 类的事实边界**：官方公告的 fact 是「某公司**宣布了** X」，不是「X 已经落地」。官方口径天然带宣传成分，`stage` 必须靠 B/C 类交叉打折（§6.2）。
- **E 类不分流会污染知识库**：KOL 文章里绝大部分是判断和预测。若不在抽取前按类型分流 prompt，模型会把「我认为字节明年会 all in Agent」当成 fact 抽出来。

### 3.3 信源注册表结构

以**域名**为主键（域名稳定，不会像 v1 那样因为 `"36氪/红薯资讯"` 这种 LLM 抽出的复合字符串而无限膨胀）。

```jsonc
{
  "id": "latepost",
  "name": "晚点 LatePost",
  "org": "media_latepost",          // 组织去重键，同组织多渠道算一个独立源
  "source_class": "B",
  "domains": ["latepost.com"],
  "channel": "rss",                 // rss | rsshub | direct | exa（实测确定，见信源实测报告）
  "channel_ref": "https://…/feed",  // RSS 地址 / RSSHub 路由 / 抓取入口
  "affiliated_with": null,          // 关联主体，报自家时不计独立源
  "reliability": 1.0,               // 人工维护权重
  "active": true
}
```

**`affiliated_with` 是 v1 缺失的关键字段**：`天下网商`（阿里系）报淘宝、`巨量引擎`（字节系）报抖音，属于"自家媒体报自家"，不能算独立信源。v1 的 `org` 去重覆盖不到这种情况。

### 3.4 信源健康度自检

每轮运行统计每个信源的：命中数 / 采纳数 / 被拒率 / 平均置信度贡献 / 最近命中时间。

用途有二：① 跑几轮后据此汰换信源；② **这张表本身是 demo 的一屏**，直接对应"信息源是否多元、可靠"的评分说明。

## 4 · 采集通道（S0）

v1 只有 Exa 一条通道，这是媒体层质量上不去的结构性原因：全部信息都依赖搜索召回，受查询词覆盖度限制，且无法定向订阅。

> **本节已按 W1 D1–D2 实测结果修订**，完整证据见 [`信源实测报告.md`](信源实测报告.md)。

| 通道 | 覆盖 | 实测数量 | 频率 | 成本 |
|---|---|---|---|---|
| **原生 / 直连 RSS** | 钛媒体、雷峰网、量子位、快手 IR、机器之心、42章经 | 6 | 每日 2 次 | 0 |
| **RSSHub** | 财新、第一财经、36氪、华尔街见闻、虎嗅、品玩、新浪科技 | 7 | 每日 2 次 | 0 |
| **直抓（SSR）** | 阿里 IR、字节招聘、巨量引擎、界面新闻、电商报 | 5 | 每周 1 次 | 0 |
| **Exa search** | 广度召回 + 交叉验证，兜底晚点/亿邦动力等无直采通道的源 | 9 | 每日 2 次 | ~$0.1/轮 |

**67% 的信源有确定性直采通道**，不依赖搜索召回。四条通道产出汇入同一张 `items` 表，用同一套核验路径处理。

**RSSHub 实例**：`rsshub.app` 实测已 403 封公共访问。主实例用 `rsshub.rssforever.com`，备用 `hub.slarker.me`，生产环境另在 GitHub Actions 用 service container 自建（`diygod/rsshub`）作第三重兜底。

**采集失败不阻断流水线**：单个通道/信源失败记入 `runs.stats.collect_errors`，其余继续。

### 4.0 公众号通道：实测不成立，改做原始出处归因

原计划把 RSSHub 微信路由作为 B/E 类主通道。实测**5 个微信路由族只有 `wechat2rss` 存活**，且其免费列表 395 个号中只命中 3 个目标（机器之心 / 量子位 / 42章经），晚点、卡兹克、字母榜、光子星球均不在内；私有部署版许可协议禁止商用与内容分发。

**改为「原始出处归因」**：深度内容首发公众号但会大量扩散到可采站点。在抽取阶段（S3）识别正文中的出处标记（「据晚点LatePost报道」「来源：字母榜」），为 item 增加：

```
item.source_id       = "36kr"      # 实际采到的载体
item.original_source = "latepost"  # 识别出的原始出处
item.source_class    = "D"         # 本条是转载
item.effective_class = "B"         # 归因后的一手性等级 ← 置信度按此计算
```

这样既保留一手性信号（不会把晚点独家误判成"单源待确认"），又让转载识别机制一鱼两吃：既做核验，又做归因。**归因结果需人工抽检**，纳入 §12 复核节点。

### 4.1 Exa 查询矩阵

v1 的问题：每家 3 条泛问（`{company} AI 电商/工具/导购`），导致 `data_bi` 和 `service_fulfillment` 两个领域没有任何对应查询词，事件必然稀疏。

改为**公司 × 领域**矩阵，5×5 = 25 格，选 15–18 个高价值格子填，保证每个领域都有召回下限：

```jsonc
{
  "matrix": {
    "taobao": {
      "retail_ops":   ["淘宝 AI 搜索推荐 上线", "淘宝 AI 导购 助手"],
      "marketing":    ["淘宝 AIGC 素材 商家"],
      "merchant_tools":["淘天 商家 AI 经营工具"],
      "data_bi":      ["阿里 电商 数据 智能 分析 产品"],
      "service_fulfillment": ["淘宝 智能客服 AI 售后"]
    }
    // ... 其余公司

  "industry": [
    "AI 电商 监管 新规", "AIGC 标识 电商 治理",

## 5 · 去重与拒绝台账

### 5.1 三层去重（S1，零 LLM 成本）

| 层 | 方法 | 判定 | 处理 |
|---|---|---|---|
| L1 URL 精确 | `url_canonical`（去 utm/参数/锚点）比对 | 完全相同 | 丢弃，记 `duplicate_url` |
| L2 内容近重复 | 正文 SimHash，汉明距离 ≤ 3 | 判定为转载 | 记 `syndication`，`merged_into` 指向已有事件 |
| L3 语义归并 | Embedding Top-K（k=8, cos>0.82）→ LLM 裁决 | 同一事件 | 归入已有事件，记归并理由 |

L3 的 LLM 裁决**必须输出理由**，理由写入台账，成为"为什么这两条是同一事件"的可查证据。

### 5.2 拒绝台账（rejects）—— 核心加分项

> v1 的设计错误：「旧闻和重复转载应该在第一步被排除掉」。
> 但评分标准要的是「**是否识别**旧闻、重复转载和待确认信息」——悄悄丢掉等于无法证明你识别了。

**每一条被淘汰的信息都要留痕**，字段：

| 字段 | 说明 |
|---|---|
| `stage` | 在哪一步被拒：`url_dedup` / `prescreen` / `simhash` / `merge` / `no_source` |
| `reason_code` | `duplicate_url` / `syndication` / `stale` / `irrelevant` / `marketing` / `merged` |
| `reason_detail` | 人话解释（如"与 EV-0012 为同一事件，本条为搜狐转载，无增量信息"） |
| `merged_into` | 归并到哪个事件 ID |

这张表在 demo 里是最有说服力的一屏，同时证明信息覆盖广度和核验严谨度。

## 6 · 核验规则（S5，纯规则，可回归）

模型只做抽取，所有可信度判断由确定性规则完成。

### 6.1 五级置信度

```python
# 独立组织数：排除与事件主体存在关联关系的信源
independent_orgs = count(distinct org
                         from accepted_items
                         where source.affiliated_with != event.company)

# 注意用 effective_class（归因后的一手性），不是 source_class（采集载体的类别）
# 例：36氪转载晚点独家 → source_class='D'，effective_class='B'，按 B 类计
has_official = exists(item where item.effective_class == 'A'
                      and item.source.affiliated_with == event.company)
has_deep     = exists(item where item.effective_class == 'B')

if has_official and independent_orgs >= 2:  confidence = "官方确认·多源印证"   # L1
elif has_official:                          confidence = "官方一手"           # L2
elif independent_orgs >= 2:                 confidence = "多源已验证"         # L3
elif has_deep:                              confidence = "深度单源"           # L4
else:                                       confidence = "单源待确认"         # L5 → 人工队列
```

**L4「深度单源」是 v1 缺失的一档。** v1 只有三档，晚点的独家报道会被判成"单源待确认"——把最有价值的信息打成了最低档。

D/E 类信源不能独立支撑一个事件。若某事件的全部 items 都是 D/E 类，该事件不入库，记 `rejects(no_source)`。

### 6.2 阶段打折规则

`stage` 的四档有序：`概念宣传 < 试点探索 < 已上线 < 规模化应用`

```python
official_stage = 从 A 类信源抽取的阶段
evidence_stage = 从 B/C 类信源抽取的阶段

if official_stage and evidence_stage:
    stage = min(official_stage, evidence_stage)      # 取保守值
    stage_basis = f"官方称{official_stage}，媒体报道显示{evidence_stage}，取保守值"
elif official_stage:
    stage = official_stage
    stage_basis = "仅官方口径，未经第三方验证"        # 前端需显式标记
else:
    stage = evidence_stage
    stage_basis = f"依据 {source_names}"
```

这条规则直接服务「相关动作处于什么阶段」这个评分点，也是官方源与媒体源互补的落点。

### 6.3 三级时间口径

v1 已标注这是个问题（"ai抽取的可靠性，尤其是关于时间的"）。时间错误会污染"新增/延续/旧闻"的全部判定。

| 优先级 | 来源 | `time_source` | 是否参与窗口硬判定 |
|---|---|---|---|
| 1 | 结构化元数据（Exa `publishedDate` / `og:published_time` / JSON-LD） | `exact` | ✅ |
| 2 | 页面可见发布时间正则提取 | `parsed` | ✅ |
| 3 | LLM 从正文推断 | `inferred` | ❌ 只进候选，UI 显示"约" |

同时保留**双时间口径**：`published_at`（原文发布）与 `discovered_at`（我方采集）。前端两个都显示。

### 6.4 状态判定（新增 / 延续 / 静默 / 旧闻）

```python
if event.first_seen_at in 本期:                      status = "新增"
elif event 在本期有新增 accepted item:                status = "延续"
elif event.event_date >= period_start - window_days: status = "静默"   # 窗口内但本期无进展
else:                                                status = "旧闻/背景"
```

直接回答「本期相比上期有哪些新增、延续或变化信号」。事件 ID 跨期稳定，存量事件本期无新信源则原样结转。

## 7 · 事实 / 推断 / 建议（claims）

> 靠 system prompt 写"要区分事实和推断"是不够的——那是靠模型自觉。评委随手抽查一条没标的，25 分就打折。

三者统一存在 `claims` 表，用 `kind` 区分，**程序层强制约束**：

| kind | 必填 | 禁止 |
|---|---|---|
| `fact` | `source_item_id` | 来源为 D/E 类 → 拒绝写入 |
| `inference` | `attributed_to`（信源名 or `assistant`）<br>若为 `assistant` 则必填 `based_on: [fact_ids]` | `based_on` 空且归属 assistant → 拒绝 |
| `recommendation` | `audience`（运营/商分/营销）<br>`needs_internal_data`（bool） | **有 `source_item_id` → 拒绝** |

**最后一条是硬边界：建议不能有信源。**
如果一条"建议"能追溯到某篇文章，那它就不是建议，是别人的观点，一律归为 `inference` 并标注 `attributed_to`。

前端三种视觉区分（事实=实心 / 推断=虚线 / 建议=独立卡片带受众标签）。

## 8 · 事件关系边（S6）

灵感来自 Obsidian 双链，但必须是**可解释的有类型边**，不是模糊关联。

| 关系 | 含义 | 生成方式 |
|---|---|---|
| `follows` | B 是 A 的后续进展 | 规则（同 company + 同 event_key 家族 + 时间序）+ LLM 确认 |
| `corroborates` | A 与 B 相互印证 | LLM 提议，须引用具体 fact |
| `contradicts` | A 与 B 存在矛盾 | LLM 提议，须引用具体 fact |
| `causes` | A 是 B 的诱因 | LLM 提议，须引用具体 fact |
| `same_actor_track` | 同一主体的动作序列 | 纯规则 |

每条边必带 `basis`（建立依据）与 `created_by`（rule / llm / human）。前端渲染为叙事链，支持从任一事件双向追溯。

**这是「洞察深度」区别于「新闻罗列」的核心载体。**

## 9 · 洞察合成（S7）

### 9.1 周报

每周一处理上一周（自然周，周一~周日），产出：

- `headline` —— 本期主线判断，≤40 字
- `key_findings[]` —— 每条含 `title` / `detail` / `evidence: [event_ids]`，数量按实际事件密度定，不凑数
- `domain_summaries{}` —— 五领域各自的本期态势 + 下期观察点
- `watchlist[]` —— 下期观察清单，每条关联 event_ids（**渲染层不外显编号**）
- `method_notes` —— 本期可信度边界：哪些结论受单源限制、哪些领域信息不足

**输入必须包含上期 watchlist**（v1 的 prompt 设计了但没真正喂进去），用于延续性检查。

历史周报全部归档入 `reports` 表，前端提供历史入口。

### 9.2 定制简报

用户选公司/领域 + 自由提示词 → SSE 流式输出。

**消息三层组装**（沿用 v1 的设计，这个是对的）：
```
system : 固定简报 prompt（行为稳定，永不被变量污染）
user   : 前段「简报范围」——服务端渲染的选项
user   : 末段 —— 用户原始提示词（永远最后，离指令出口最近，遵从权重最高）
```

SSE 推送真实 `thinking` 事件（分析参数 / 检索事件 / 提取事实 / 生成洞察 / 组装内容），**不是前端编造的假进度**。

输出 Markdown + ` ```echarts ` 代码块（ECharts option JSON，不含函数）+ Mermaid。

## 10 · 前端设计

**硬约束：能读、不崩、手机能看，达到就停手。**

### 10.5 辅助页

- `/sources` 信源健康度表（§3.4）
- `/method` 方法论与运行说明（§13，直接对应交付要求）

### 10.6 稳定性红线

评委可能凌晨点、可能用手机点：

- **静态降级数据**：API 挂了页面照常可读（v1 这个设计是对的，保留）
- **移动端从第一天就按响应式写**，不要像 v1 那样最后一天补
- 数据永不为空（部署前确保至少两期数据）

## 12 · 人工复核（HITL）

「运行说明」明确要求写清人工复核节点。v1 全自动跑完，没有人在环。

三个节点，均在**本地 CLI**（不上线）。工作流：`git pull` → `rebuild` → 复核 → `dump` → `commit` → `push`，下一轮流水线自动带上复核结果。操作留痕进 `reviews`：

| 节点 | 动作 | 触发时机 |
|---|---|---|
| **信源分级维护** | 调整 `source_class` / `reliability` / `active` | 按需 + 每月看健康度表 |
| **待确认队列裁决** | L5 单源事件：确认 / 驳回 / 继续观察 | 每期运行后 |
| **归并纠错** | 拆分误合并的事件 | 发现时 |

**复核界面不上线，但复核记录要展示在线上**（"本期人工复核 N 次，其中确认 X / 驳回 Y"）。

## 14 · 数据模型

以下是 SQLite 的建表语句。**注意**：SQLite 是运行时索引（gitignore），真相源是 `data/*.jsonl`——每张表对应一个同名 JSONL 文件，一行一条记录，字段与列一一对应。`rebuild` 命令从 JSONL 重建 DB，`dump` 命令从 DB 写回 JSONL（见 §2.2）。

```sql
-- 信源注册表
CREATE TABLE sources (
  id              TEXT PRIMARY KEY,
  name            TEXT NOT NULL,
  org             TEXT NOT NULL,
  source_class    TEXT NOT NULL CHECK(source_class IN ('A','B','C','D','E')),
  domains         TEXT,                      -- JSON array
  channel         TEXT NOT NULL,             -- rsshub|exa|direct
  channel_ref     TEXT,
  affiliated_with TEXT,                      -- 关联主体 company_id
  reliability     REAL DEFAULT 1.0,
  active          INTEGER DEFAULT 1,
  note            TEXT
);

-- 原始条目（一条 URL = 一条 item）
CREATE TABLE items (
  id            TEXT PRIMARY KEY,            -- sha1(url_canonical)[:16]
  url           TEXT UNIQUE NOT NULL,
  url_canonical TEXT NOT NULL,
  title         TEXT NOT NULL,
  content       TEXT,
  source_id     TEXT REFERENCES sources(id),
  source_class  TEXT,                        -- 冗余，未登记源默认 'D'
  published_at  TEXT,
  time_source   TEXT CHECK(time_source IN ('exact','parsed','inferred')),
  discovered_at TEXT NOT NULL,
  run_id        TEXT REFERENCES runs(id),
  simhash       TEXT,
  embedding     BLOB,
  status        TEXT,                        -- pending|accepted|rejected|merged
  event_id      TEXT REFERENCES events(id),
  raw           TEXT                         -- 原始响应，完整留档
);

-- 事件（同一事件只一条）
CREATE TABLE events (
  id               TEXT PRIMARY KEY,         -- EV-0001，跨期稳定
  event_key        TEXT NOT NULL,
  title            TEXT NOT NULL,
  summary          TEXT,
  company          TEXT NOT NULL,
  domains          TEXT,                     -- JSON array
  stage            TEXT,
  stage_basis      TEXT,
  confidence       TEXT,
  status           TEXT,
  first_seen_at    TEXT,
  last_update_at   TEXT,
  event_date       TEXT,
  independent_orgs INTEGER,
  review_state     TEXT DEFAULT 'none'
);

-- 事实 / 推断 / 建议
CREATE TABLE claims (
  id                  TEXT PRIMARY KEY,
  event_id            TEXT REFERENCES events(id),
  kind                TEXT NOT NULL CHECK(kind IN ('fact','inference','recommendation')),
  text                TEXT NOT NULL,
  source_item_id      TEXT REFERENCES items(id),
  based_on            TEXT,                  -- JSON array of claim_ids
  attributed_to       TEXT,
  audience            TEXT,
  needs_internal_data INTEGER
);

-- 事件关系边
CREATE TABLE edges (
  id         INTEGER PRIMARY KEY,
  from_event TEXT REFERENCES events(id),
  to_event   TEXT REFERENCES events(id),
  relation   TEXT NOT NULL,
  basis      TEXT NOT NULL,
  created_by TEXT NOT NULL                   -- rule|llm|human
);

-- 拒绝 / 归并台账
CREATE TABLE rejects (
  id            INTEGER PRIMARY KEY,
  run_id        TEXT REFERENCES runs(id),
  item_id       TEXT,
  url           TEXT,
  title         TEXT,
  source_name   TEXT,
  stage         TEXT NOT NULL,
  reason_code   TEXT NOT NULL,
  reason_detail TEXT,
  merged_into   TEXT,
  created_at    TEXT
);

-- 运行记录（漏斗回放的数据源）
CREATE TABLE runs (
  id          TEXT PRIMARY KEY,              -- RUN-20260908-0830
  started_at  TEXT, finished_at TEXT,
  mode        TEXT,                          -- live|mock
  dataset     TEXT,                          -- ecommerce|<行业2>
  stats       TEXT,                          -- JSON: 各阶段计数
  cost        TEXT,                          -- JSON: exa/llm/embedding 成本
  config_hash TEXT                           -- 配置指纹，证明可复现
);

-- 人工复核留痕
CREATE TABLE reviews (
  id          INTEGER PRIMARY KEY,
  target_type TEXT,                          -- event|source|merge
  target_id   TEXT,
  action      TEXT,                          -- confirm|reject|split|retier|watch
  note        TEXT,
  reviewer    TEXT,
  created_at  TEXT
);

-- 周报归档
CREATE TABLE reports (
  id           TEXT PRIMARY KEY,             -- W-2026-W37
  period_start TEXT, period_end TEXT,
  headline     TEXT,
  body         TEXT,                         -- JSON
  generated_at TEXT,
  run_id       TEXT REFERENCES runs(id)
);

-- 全文检索
CREATE VIRTUAL TABLE items_fts USING fts5(title, content, content=items);
```

## 18 · v1 经验教训（为什么重做）

**表面症状**：CI 里 `npm ci` 挂死 44 分钟、网络不稳。

**真正的问题**：
1. **同一套东西有 4 份实现** —— `cf-worker/`（Hono 生产后端）+ `server/`（FastAPI 参照实现）+ `web/index.html`（4726 行单文件早期版）+ `react-web/`。
2. **数据散在 6 个 JSON 文件里，没有单一真相源。**
3. **精力被前端打磨吃掉** —— 交接文档最后 30% 全在修 tab 下划线动画、弹窗层级栈、顶距参差，这些一分不加。

**v2 的三条纪律**：一个后端、一个前端、一个数据真相源。

**从 v1 直接继承的资产**：
- `org` 组织去重设计（同公司多渠道算一个独立源）—— 正确，保留并补 `affiliated_with`
- 置信度纯规则、模型只抽取不裁决 —— 正确，扩展为五级
- `--mock` 确定性回放 —— 保留并加强
- 简报消息三层组装 —— 正确，原样保留
- SSE 真实 thinking 事件驱动 —— 正确，原样保留
- 前端静态降级数据 —— 正确，保留
- `domain_map` —— 升格为信源注册表主键
