> 完整设计见 [`技术方案.md`](技术方案.md)。

---

## 0 · 一句话立场

**严谨性由数据结构保证，不由提示词祈祷。**

「让模型只输出确认过的信息」是一句无法验证的祈使句。同样的输入，
同样的提示词，两次调用可以给出不同的谨慎程度，而且没有任何地方能查到
它这次到底谨慎在哪。

所以本项目把所有可判定的东西从提示词里搬出来，做成规则：

| 判断 | 谁来做 | 为什么 |
|---|---|---|
| 这条信息说了什么 | 模型 | 语言理解，规则做不了 |
| 这条信息属于哪一类 | 模型 | 同上 |
| **这个事件可信到什么程度** | **规则** | 输入相同则输出相同，可回归、可审计、可追责 |
| **这个事件处在什么落地阶段** | **规则** | 同上 |
| **这个事件是新增还是旧闻** | **规则** | 同上 |

模型负责抽取，规则负责裁决。分界线画在「能不能用确定性函数算出来」。

## 1 · 一手性：分层轴是距离，不是身份

最容易走错的一步，是按发布主体的名气分层——官方最高、大媒体次之、自媒体最低。
这个轴是错的。正确的轴是**这条信息离事件现场有多近**。

| 类 | 定义 |
|---|---|
| **A** 当事方直述 | 官方公告 / 财报 / 招聘 JD / App 更新日志 |
| **B** 原创深度报道 | 有独立采访、内部信源、实地调查 |
| **C** 常规媒体报道 | 基于公开信息的日常报道 |
| **D** 聚合转载 | 无增量信息的搬运 |
| **E** 观点评论 | 个人判断与分析 |

按这个轴，**晚点的独家比公司的 AI 公关稿更接近一手**——公关稿离「实际发生了
什么」隔着一层修辞，独家隔着的是记者，但记者拿到的是内部信源。
身份轴会把这两者的次序搞反。

### 1.1 载体与出处要分开记

36 氪转载晚点的独家：**采集载体**是 36 氪（D 类），**原始出处**是晚点（B 类）。
如果只记载体，这条会被当成转载稿降级掉；如果只记出处，又无法追溯是从哪
采到的。所以三个字段各司其职：

```
source_id        采集载体      36kr
original_source  原始出处      晚点 LatePost
effective_class  归因后一手性   B      ← 核验规则只认这个
```

核验规则一律用 `effective_class`，不用 `source_class`。

### 1.2 分层的意义在于核验路径不同

分层不是为了给信源打分排座次，是为了让不同类走不同的验证路径：

| 类 | 需要多源交叉？ | 特殊约束 |
|---|---|---|
| A | 不需要 | 但**落地阶段要打折**——官方口径 ≠ 已落地 |
| B | 不强制 | 单源即可进「深度单源」档 |
| C | **必须** | 单源只能是「待确认」 |
| D | — | 不计独立信源，只作归并证据 |
| E | — | **禁止抽取事实**，只抽判断 |

E 类禁止产出 fact，是在提示词和程序两层同时约束的：提示词里说明，
抽取结果里再过滤一遍。只靠提示词的约束等于没有约束。

## 2 · 置信度：五档，纯规则算出来

```
官方确认·多源印证   有 A 类直述  且  独立组织数 ≥ 2
官方一手           有 A 类直述
多源已验证                        独立组织数 ≥ 2
深度单源           有 B 类深度报道
单源待确认         以上都不满足
```

两个输入：有没有 A 类、有没有 B 类、独立组织数。都是确定性的。
换一批数据重跑，同样的输入必然得到同样的档位。

### 2.1 独立组织数：按 org 去重，不按信源去重

同一家机构的多个渠道算一个组织。36 氪的网站、36 氪的公众号、
36 氪的头条号报道同一件事，这不是三个独立信源，是同一个编辑部发了三次。
所以信源注册表里每个信源都挂一个 `org`，计数按 `org` 去重。

### 2.2 自家媒体不计独立信源

`affiliated_with` 字段记录信源与观察主体的从属关系。天下网商报道阿里，
这不是独立印证——它是阿里旗下的。这类信源在计算该主体事件的独立组织数时
直接跳过；但如果它是当事方官方渠道（A 类），仍然计入 `has_official`。

这一条在实测里生效过：如果不排除，若干阿里事件会从「单源待确认」
虚假升档到「多源已验证」。

## 3 · 落地阶段：官方口径要打折

四个阶段：概念宣传 → 试点探索 → 已上线 → 规模化应用。

行业惯例是把试点说成上线，把上线说成规模化。这是**已知的系统性偏差**，
不是偶发噪声，所以要用规则修正而不是指望模型自己警惕：

```
stage = min(官方自述的阶段, 第三方报道显示的阶段)
```

取保守值，并把依据记进 `stage_basis`，页面上直接展示
「官方称『已上线』，第三方报道显示『试点探索』，取保守值」。

抽取阶段的提示词明确要求**不要自己打折**——如实记录这条报道说了什么，
打折是下游规则的职责。让模型同时承担抽取和裁决，两个职责会互相污染。

> **诚实的边界**：这条规则目前全库只触发过 1 次。不是因为 A 类信源没有了——
> 接入美团技术团队 RSS 之后 A 类条目已有 20 条、支撑 17 个事件——而是因为
> 打折需要**官方与第三方同时报道同一件事**，这个重叠仍然稀少。
> 多数 A 类事件是官方单方面披露，`stage_basis` 记的是「仅官方口径，未经第三方验证」。
> 机制是对的，样本不支持说它已被验证有效。

## 4 · 事实 / 推断 / 建议：用程序约束，不用提示词

三类断言，各自有硬性的结构约束：

| 类型 | `source_item_id` | 约束 |
|---|---|---|
| `fact` 事实 | **必须有** | 且不得来自 D / E 类信源 |
| `inference` 推断 | 可有 | 必须标注 `attributed_to`（谁的判断） |
| `recommendation` 建议 | **必须没有** | 只能在周报合成阶段产出 |

「建议不能有信源」这条初看反直觉，但它是整套设计里最重要的一条：
**能追溯到某篇文章的就不是建议，是别人的观点**。别人的观点属于 inference，
要标明是谁说的。真正的建议只能由本系统基于全局事实生成，因此它只有一个
产出点——周报合成（S7），并且必须带 `audience`（运营 / 商分 / 营销）与
`needs_internal_data`。

公开信息无法验证的效果类判断一律标 `needs_internal_data: true`。
这不是免责声明，是告诉读者这条建议要落地还缺什么。

各类断言的实时条数见 [`作品文档.md`](作品文档.md) 的效果验证一节。

## 5 · 拒绝台账：不丢弃，只降级并记账

「识别出旧闻 / 转载 / 待确认」本身就是产出。悄悄丢掉等于没做——
读者无从判断你是筛掉了噪声，还是根本没采到。

所以每一条被淘汰的信息都写进 `rejects` 台账，带上是在哪一级、
因为什么原因被拦下的。当前台账：

<!-- live:rejects -->
| 拦截层 | 条数 |
|---|---|
| `keyword_filter` | 3,698 |
| `url_dedup` | 1,567 |
| `window` | 168 |
| `prescreen` | 157 |
| `title_dedup` | 100 |
| `jina_title_filter` | 36 |
| `extract` | 30 |
| `merge_cross` | 22 |
| `merge` | 17 |
| `human_review` | 1 |
<!-- /live -->

台账的另一个作用是让漏斗的每一级都可被质疑。有一次 `jina_title_filter`
这一层记了 0 条——因为代码里有个「一条都没匹配上就退化为抓最新 N 篇」的
兜底分支，走兜底时不写台账。**是这个 0 暴露了那条静默路径**，
否则它会一直悄悄浪费抓取额度。

## 6 · 时间：三级口径，来源不同不能混用

| 口径 | 含义 | 参与窗口硬判定？ |
|---|---|---|
| `exact` | 原文明确给出的发布时间 | 是 |
| `parsed` | 从标题或正文里解析出的日期 | 是 |
| `inferred` | 只能推断（如「本周」「近日」） | **否** |

推断出的时间不参与「新增 / 旧闻」的硬判定。把 `inferred` 当成 `exact` 用，
会让一批时间模糊的旧闻混进本周新增。

另外，事件的时间锚点是 `event_date`（事情发生的时间），不是
`first_seen_at`（系统发现的时间）。这两个混用会导致回填的历史事件全部
被标成「新增」——这个 bug 出现过，一次拦下了 87 条追溯性事件。

同理，周报的周期口径是**事件发生周**而不是「本轮采集到」。前者回答
「上周行业发生了什么」，是读者对周报的预期，也让历史回填成为可能；
后者只反映系统何时发现，无法回溯。

## 7 · 归并：宁可漏掉，也不要误合并

同一件事被多家报道，要合成一个事件；不同的事被误判成一件，
会直接污染独立组织数，进而虚高置信度。所以归并的默认倾向是保守。

但「保守」一开始被写成了二选一：合并 or 不合并，提示词里强调宁可漏掉。
结果模型交回了空数组——它不敢做任何判断。**强迫在不确定的地方做二元决策，
得到的不是保守，是弃权。**

修法是给不确定性一个落点：输出增加 `suspects` 一档，模型可以说
「这两个我拿不准」，系统把它们标成 `suspect_duplicate` 进人工复核队列。
不确定性被显式表达出来，而不是被压成一个假的确定答案。

归并还踩过两个坑，都是「静默丢失」这一类：

- **孤儿候选**：模型返回的分组没有覆盖全部候选，未被分配的 11 条被静默
  丢弃。修法是把未分配的候选各自独立成事件。
- **归并调用失败**：某公司的归并 LLM 调用失败时，它的候选永远停在
  `extracted` 状态。一次运行事件数从 129 掉到 79，**51 条凭空消失**。
  修法是加逐候选的降级兜底——调用失败就每条独立成事件，并记
  `merge_fallback` 计数。

这两个坑的共同点：失败路径没有出口，数据就悄悄漏掉了。
任何一条数据都必须有归宿——要么入库，要么进台账。

### 7.1 向量该用在召回，不该用在判定

跨事件归并原本是把全部事件塞进一次 LLM 调用整体通读。事件涨到 133 个之后
实测发现：余弦相似度最高的 8 对**全是真重复**，而整表通读一对都没抓到——
其中一对标题只差一个引号（`"AI万相"` 与 `“AI万相”`）。长列表里模型会漏。

改成向量召回 + 逐对裁决后，一次跑出 19 个该合并的重复事件。

但同一批标定也划出了向量的边界。拿「同一事件内的条目」当正样本、
「不同事件的条目」当负样本量了一遍：

| | 中位 | p99 |
|---|---|---|
| 同一事件内 | 0.793 | — |
| 不同事件间 | 0.520 | 0.758 |

两个分布重叠得厉害。阈值取到零误伤（0.92）只能抓住 6% 的同事件对；
放宽到能抓住多数，就会开始误合并。**所以向量不能当自动去重的判据**——
它是个好的排序信号（0.793 vs 0.520 区分度很强），不是个好的分类器。

这条边界决定了它在系统里的位置：向量负责把「值得比较的对」从
八千多个组合里挑出一百个，是不是同一件事仍然由 LLM 判断，
拿不准的进人工队列。**召回可以宽，判定必须严。**

## 8 · 人工复核：状态必须有粘性

S5 核验是**全库重算**。这个设计本身是对的——规则改了要能对历史数据重跑。
但它带来一个必然的副作用：任何不能从持久化数据重建的东西，都会被它抹掉。

踩过两次，都是同一类：

1. **人工复核结论被洗掉**。每轮跑批把所有单源事件重置回 `pending`，
   批量裁决的结果全部作废。修法是给已裁决状态加粘性。
2. **落地阶段全库失效**。S3 抽出的 stage 只暂存在内存字典里，S5 重算时
   老事件查不到，被写回 `NULL`。全库事件的阶段全是空的，
   §3 那套打折规则事实上从未生效过。修法不是加缓存，
   是把中间结果落到 `items.draft_stage` 列上，进 JSONL 真相源。

**教训是通用的**：只要存在全库重算，中间结果就必须持久化。
内存缓存在单轮内看起来完全正常，跨轮才暴露。

## 9 · 无人值守：失败必须有出口，成功必须可验收

流水线每天自己跑两轮，没有人盯着。这带来两条额外的纪律。

**第一，任何一步的失败都不能带走整轮的成果。**
S2–S7 原本是一串裸调用，任一阶段抛异常，后面的 `store.dump()` 就到不了——
本轮采到的东西全部丢失，CI 也不会提交任何数据。一次模型 429 或网络抖动，
代价是整轮作废。现在每个阶段都包了兜底：失败记进运行档案、打印出来、
继续往下跑。S5 是对全库重算的纯规则，前面失败它照样该跑。

配套的是回放打印也要能容忍空结果——早先它直接 `llm_stats["verify"]["events"]`，
阶段失败时这行自己会抛异常，把 `dump()` 一起带走，
「为了不丢数据加的容错」反倒成了丢数据的原因。

**第二，「作业成功」不是验收标准。**
定时任务连续多天报绿灯，线上数据却一直没变：workflow 只提交了 JSONL，
既没跑 export 也没提交 API 快照，而线上读的正是后者。每一步都成功，
闭环却不存在。可验收的标准只有一个——**线上的数字有没有跟着变**。

## 10 · 这套方法不主张什么

同样重要的是划清边界：

- **不主张能发现独家。** 采的全是公开信息，价值在结构化和交叉核验，
  不在信息本身的稀缺性。
- **不主张置信度等于真实性。** 「多源已验证」只说明有两个独立组织报道过，
  不代表事情为真——多家媒体转同一个错误通稿的情况是存在的，
  所以才要按 org 去重、要排除自家媒体。
- **不主张建议可以直接执行。** 所有涉及我方业务的建议都标注
  「需内部数据验证」，因为公开信息看不到我方的成本结构和存量能力。
- **不主张覆盖完整。** 当前 Exa 贡献了八成条目，检索服务的召回偏好会
  直接传导为覆盖偏差。没被检索到的事情，这个系统不知道自己不知道。

## 11 · 方法的自我证伪

本项目的工作方式是：**实现 → 真跑一轮 → 让数据暴露问题 → 修 → 把推理过程
写进代码注释和提交信息**。上面列出的绝大多数问题，都不是读代码读出来的，
是跑出来的。

有几处是系统自己报出来的：

- 周报的「方法论备注」里，模型指出本期两个事件疑似同一件事——
  这是归并漏判，是被自己的产出物抓到的。
- 拒绝台账里 `jina_title_filter` 层的 0 条记录，暴露了一条静默的兜底路径。
- 事件阶段分布 100% 为空，暴露了整条打折链路的失效。

几个被实测推翻的初始判断，一并记在这里：

| 初始判断 | 实测结果 |
|---|---|
| RSSHub 是 B/E 类信源的主通道 | 5 个路由族里 4 个已失效，只剩 wechat2rss 且免费档只覆盖 3 个目标 |
| 首页 SSR 字符数可作为「可直抓」的判据 | 抓回来的是「投资者关系」「文化与价值观」这类导航链接，判据无效 |
| SimHash 能覆盖转载去重 | 指纹算的是标题+正文，不同站点的模板差异让同标题稿件指纹不同；补了标题归一化精确匹配才捞到 |
| Agent Reach 可以补充信源 | 实际安装测试后判定价值不足，未接入 |

写下来不是为了显得坦诚，是因为这些结论下一个人还会再撞一次。
