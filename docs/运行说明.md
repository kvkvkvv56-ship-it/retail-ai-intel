## 1 · 系统在做什么

每天两轮，从 34 个登记信源采集公开信息，经过七级漏斗产出结构化事件库，
每周合成一份洞察周报，并支持按需生成定制简报。

```
S0 采集    六通道并行取原始条目
S1 去重    URL 规范化 → SimHash → 标题归一化，全部留痕
S2 预筛    便宜档模型判断是否与观察范围相关
S3 抽取    强档模型按信源一手性分流，抽成结构化事件草稿
S4 归并    按公司通读聚类，同一件事的多篇报道合成一个事件
S5 核验    纯规则裁决置信度 / 落地阶段 / 状态，模型不参与
S6 关系边  同主体动作序列（规则）+ 模型提议的语义关系
S7 洞察    周报合成，是 recommendation 的唯一产出点
```

**我方视角**：本站服务于京东零售。每个事件都要求给出对我方的启示——
竞对压力、可借鉴做法、或上游能力带来的新可能。京东自身的动态同样观察，
追踪自家公开足迹是竞对情报的常规做法。

## 4 · 本地运行

需要 Python 3.11+ 与 Node 18+。

```bash
cp .env.example secrets.env   # 填入自己的 key
chmod 600 secrets.env
source secrets.env
```

需要的环境变量：

| 变量 | 必需 | 用途 |
|---|---|---|
| `KB_LLM_API_KEY` | 是 | DeepSeek API key，S2/S3/S4/S7 全部走它 |
| `KB_LLM_BASE_URL` | 否 | 默认 `https://api.deepseek.com` |
| `KB_SCOUT_MODEL` / `KB_STRONG_MODEL` | 否 | 默认均为 `deepseek-chat` |
| `EXA_API_KEY` | 否 | 缺失或 `--no-exa` 时跳过 exa 通道 |
| `JINA_API_KEY` | 否 | 缺失时跳过 jina 通道（匿名额度实测会被封） |

跑一轮完整流水线：

```bash
python3 -m pipeline.run --dataset ecommerce
```

常用变体：

```bash
python3 -m pipeline.run --no-exa      # 零外部检索成本，只走订阅与聚合通道
python3 -m pipeline.run --stage collect   # 只采集，不调 LLM
python3 -m pipeline.run --mock        # 用 data/mock_llm/ 的固定回放替换全部 LLM 调用
python3 -m pipeline.run --rebuild     # 从 data/*.jsonl 重建 intel.db 后退出
```

生成前端所需的 API 快照，然后本地预览：

```bash
python3 -m pipeline.export
cd web && npm install && npm run dev
```

## 5 · 定时运行

`.github/workflows/pipeline.yml`，北京时间 08:30 / 20:30 各一轮
（cron 写的是 UTC 00:30 / 12:30）。晚场加 `--no-exa` 以控制检索额度。

仓库 Actions secrets 需要 `EXA_API_KEY` 与 `KB_LLM_API_KEY`。
流水线跑完把 `data/*.jsonl` 与 `web/public/api/` 提交回仓库——
JSONL 是真相源，行级 diff 让「这一轮改了什么」在 GitHub 上直接可读。

关键路径只有 Python。前端构建与部署不在定时任务里，避免 npm 侧的
波动阻断数据更新。

## 6 · 部署

Cloudflare Workers + 静态资源绑定，自定义域 `ai.kvkvkvv.site`。

```bash
cd web && npm run build
npx wrangler deploy
```

Worker（`worker/index.ts`）承担两件事：把 `/api/v1/*` 的静态快照透出去，
以及定制简报的三段式在线生成（意图解析 → 知识库+互联网检索 → 报告撰写），
后者需要 `KB_LLM_API_KEY` 与 `EXA_API_KEY` 作为 Worker secrets。

## 7 · 人工复核

三个复核节点，全部走 CLI，每次裁决都写进 `data/reviews.jsonl` 并在
「信源」页展示聚合结果。

```bash
python3 pipeline/review.py queue                      # 看待办队列
python3 pipeline/review.py event EV-xxxxxxxx watch    # 单个事件裁决
python3 pipeline/review.py batch pending watch --note "理由"   # 批量，只记一条
python3 pipeline/review.py merge EV-aaa EV-bbb split  # 归并纠错
python3 pipeline/review.py source latepost --class B  # 信源分级维护
```

复核状态具备粘性：`stage_verify` 每轮对全库重算，但已裁决过的事件
（`watching` / `confirmed` / `rejected` / `suspect_duplicate`）不会被重置回
`pending`。这条是踩过坑之后加的——早先每轮跑批都会把人工结论洗掉。

## 8 · 数据布局

```
data/
  items.jsonl      原始条目（505）
  events.jsonl     事件（126）
  claims.jsonl     事实 / 推断 / 建议（1,283）
  edges.jsonl      事件关系边（133）
  rejects.jsonl    拒绝台账（2,841）
  reviews.jsonl    复核记录（人工 14 / 系统自动标记 17）
  reports.jsonl    周报（6）
  runs.jsonl       运行记录（7）
  llm_cache.jsonl  LLM 调用缓存，按 sha1(model+messages) 命中
intel.db           SQLite 运行时索引 + FTS5，gitignore，随时可重建
```

JSONL 是真相源，SQLite 是可丢弃的索引。`store.dump()` 与 `store.rebuild()`
双向同步，clone 之后 `--rebuild` 五秒内可查。

新增字段时必须同时改三处：`SCHEMA` 的建表语句、`TABLES` 的列清单
（决定 dump/rebuild 的字段范围）、以及 `Store._migrate()`——
`CREATE TABLE IF NOT EXISTS` 不会给已存在的表补列，漏了这一步老库跑新代码
会静默走空值分支。

## 9 · 成本

以最近一次完整轮次（`RUN-20260906-1738`）为准：

| 项 | 用量 | 成本 |
|---|---|---|
| LLM | 154 次调用，输入 289,188 token / 输出 57,238 token | ¥0.75 |
| Exa | 37 次检索 | $0.26 |

单轮约 ¥2.6。每天两轮、晚场免 Exa，月成本约 ¥60。
`--mock` 实测 0 次 LLM 调用、¥0 跑通 S0–S7。注意它只替换模型调用，
采集通道仍走网络；`--mock --no-exa` 组合下外部检索成本也为零。

## 10 · 换一个行业

设计目标是「换行业只改配置」。需要动的是两个 JSON：

- `config/<dataset>.json`——观察主体、领域、检索矩阵、相关性关键词、窗口
- `config/sources.<dataset>.json`——信源注册表及其一手性分级与采集通道

提示词是**配置驱动**的：`prompts.py` 里的公司枚举、领域枚举、阶段枚举全部
从 config 读取。早先这些是硬编码的，往 config 里加主体不会影响 LLM 阶段，
扩充是假的；这条是修过的坑，不是设计上的先见之明。

然后 `python3 -m pipeline.run --dataset <dataset>`。

## 11 · 已知局限

诚实列出，不粉饰：

1. **A 类信源产出极少。** 505 条原始条目里只有 2 条是当事方直述。
   直接后果是「官方确认」「官方一手」两档置信度目前 0 个事件命中，
   §6.2 的官方口径打折规则全库只触发过 1 次。机制正确，样本不足。
2. **RSSHub 公共实例不稳定。** 最近一轮 36 氪与新浪科技的全部实例超时，
   记入 `collect_errors` 但不阻断流水线。
3. **付费墙信源只能拿到标题与导语**，落库标记 `partial_content`。
4. **单源事件占比高。** 126 个事件里 110 个只有 1 个独立组织支撑，
   一律标「单源待确认」或「深度单源」并进复核队列，不隐藏。
5. **Exa 依赖度过高**（八成条目），检索服务的召回偏好会传导为覆盖偏差。
6. **未接入需登录的内容**，商家后台、内部群、付费社群一律不采。
7. **落地阶段依赖报道措辞。** 官方常把试点说成上线，交叉打折只在同一事件
   同时有 A 类与非 A 类信源时才生效——目前极少满足。

## 12 · 安全与合规边界

- 只采集**公开可访问**信息，遵守 robots.txt，不绕过登录墙与付费墙
- 正文只保留截断摘录与原文链接，不存储也不再分发第三方全文
- AIHOT 作为发现渠道接入：其公开使用规则对个人非商业与组织内部使用免费，
  本项目为内部审阅与个人使用、不对外分发。落库一律用原文链接，
  信源按原文发布方归属而非记为 AIHOT
- 竞对信息全部来自公开渠道，不涉及任何非公开信息获取
- 输出仅供内部研究参考，**不构成投资建议**
- 涉及我方业务的借鉴建议均标注「需内部数据验证」
