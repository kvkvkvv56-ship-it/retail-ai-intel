## 1 · 系统在做什么

> 数据类数字是 2026-09-07 的快照；流水线每天两轮持续运行，站上只会更高。

每天两轮，从登记信源采集公开信息，经过七级漏斗产出结构化事件库，
每周合成一份洞察周报，并支持按需生成定制简报。

```
S0 采集    六通道并行取原始条目
S1 去重    URL 规范化 → SimHash → 标题归一化，全部留痕
S2 预筛    便宜档模型判断是否与观察范围相关
S3 抽取    强档模型按信源一手性分流，抽成结构化事件草稿
S4 归并    按公司通读聚类，同一件事的多篇报道合成一个事件
S5 核验    纯规则裁决置信度 / 落地阶段 / 状态，模型不参与
S6 关系边  同主体动作序列（规则）+ 模型提议的语义关系
S7 洞察    周报合成，是 recommendation 的唯一产出点
```

**我方视角**：本站服务于京东零售，每个事件都要求给出对我方的启示。
京东自身的动态同样观察——追踪自家公开足迹是竞对情报的常规做法。

## 4 · 本地运行

需要 Python 3.11+ 与 Node 18+。

```bash
cp .env.example secrets.env   # 填入自己的 key
chmod 600 secrets.env
source secrets.env
```

需要的环境变量：

| 变量 | 必需 | 用途 |
|---|---|---|
| `KB_LLM_API_KEY` | 是 | DeepSeek API key，S2/S3/S4/S7 全部走它 |
| `KB_LLM_BASE_URL` | 否 | 默认 `https://api.deepseek.com` |
| `KB_SCOUT_MODEL` / `KB_STRONG_MODEL` | 否 | 默认均为 `deepseek-chat` |
| `EXA_API_KEY` | 否 | 缺失或 `--no-exa` 时跳过 exa 通道 |
| `JINA_API_KEY` | 否 | 缺失时跳过 jina 通道（匿名额度实测会被封） |

跑一轮完整流水线：

```bash
python3 -m pipeline.run --dataset ecommerce
```

常用变体：

```bash
python3 -m pipeline.run --no-exa      # 零外部检索成本，只走订阅与聚合通道
python3 -m pipeline.run --stage collect   # 只采集，不调 LLM
python3 -m pipeline.run --mock        # 用 data/mock_llm/ 的固定回放替换全部 LLM 调用
python3 -m pipeline.run --rebuild     # 从 data/*.jsonl 重建 intel.db 后退出
```

生成前端所需的 API 快照，然后本地预览：

```bash
python3 -m pipeline.export
cd web && npm install && npm run dev
```

## 5 · 定时运行

`.github/workflows/pipeline.yml`，北京时间 08:30 / 20:30 各一轮
（cron 写的是 UTC 00:30 / 12:30）。晚场加 `--no-exa` 以控制检索额度。

**补位轮**：GitHub 的 schedule 是尽力而为，会延迟甚至整条丢弃（实测 12:30
那轮推迟到 15:36，另一轮根本没触发）。所以每个正式档后各挂两条补位 cron
（+1h / +2h），开跑前先看 `data/runs.jsonl` 最后一条——距上次不足 6 小时
就跳过，只花十几秒。两个正式档相隔 12 小时，不会互相误杀。
晚场判定按 cron 的小时字段（UTC ≥ 12），不是匹配具体表达式，
否则补位的晚场会误跑 Exa。

仓库 Actions secrets 需要 `EXA_API_KEY`、`KB_LLM_API_KEY`，
可选 `JINA_API_KEY`。

每轮的动作：

```
跑流水线 (S0–S7)  →  python -m pipeline.export  →  提交 data/ 与 web/public/api/
```

**export 这一步不能省。** Worker 读的是 `web/public/api/` 里的 JSON 快照而非
JSONL。早先 workflow 只提交 JSONL，结果作业连续多天绿灯、线上数据一动不动。

关键路径只有 Python，前端构建与部署不在定时任务里。

### 5.1 数据怎么到达线上

```
流水线提交 → 仓库 web/public/api/v1/*.json
                 ├─ raw.githubusercontent   Worker 优先读（3 秒超时，600 秒边缘缓存）
                 └─ Cloudflare ASSETS       读不到时兜底（部署时打包的版本）
```

数据更新因此**不需要重新部署**，也就不需要在 CI 里存放 Cloudflare API token。
代码改了才需要 `wrangler deploy`。最坏情况（raw 不可达）等同于只读 ASSETS，
即改动之前的行为。

代价是延迟：raw 自身有约 5 分钟 CDN 缓存，叠加 Worker 侧 600 秒边缘缓存，
数据落地到线上最慢约 15 分钟。对每天两轮的情报站这个量级完全够用，
但要知道它不是秒级同步。

验收标准只有一条：**线上的数字有没有跟着变**。作业绿灯不算数。

### 5.2 阶段级容错

S2–S7 每个阶段都包了失败兜底。某阶段抛异常时，错误记入运行档案的
`stage_errors`，打印出来，并继续跑后面的阶段——不让单点故障带走整轮
已完成的工作（S5 是纯规则的全库重算，前面失败它照样该跑）。

`stage_errors` 会出现在 GitHub Actions 的运行摘要里，不会被绿灯掩盖。

## 6 · 站内文档

`docs/*.md` 由 `pipeline/docs_export.py` 导出成 API 快照，前端 `/docs`
渲染成开发者文档样式（三栏：文档目录 / 正文 / 本页目录）。

改完 markdown 跑一次 `python3 -m pipeline.export` 即可上线，
不需要另一套发布流程——文档和数据走的是同一条链路。

新增一份文档：在 `docs_export.py` 的 `REGISTRY` 里加一行
`(文件名, id, 分组, 一句话说明)`，顺序即侧边栏顺序。

## 7 · 部署

Cloudflare Workers + 静态资源绑定，自定义域 `ai.kvkvkvv.site`。

```bash
cd web && npm run build
npx wrangler deploy
```

> **踩过的坑：两个 Worker 抢同一个域名。**
> v1 的 Worker（`ai-intel-station`）在它自己的 `wrangler.jsonc` 里同样声明了
> `ai.kvkvkvv.site` 这个 custom domain，而它那个仓库的定时任务还在跑、
> 每轮都会重新部署。custom domain 的归属是**谁后部署谁生效**，于是线上会在
> v1 与 v2 之间来回切换——表现为「刚验证完是好的，过一会儿打开是另一个站」，
> 而且没有任何报错。
>
> 排查时容易被带偏：症状看起来像前端样式没生效或缓存问题，实际两边是不同的
> 构建产物。判据是看页面上有没有对方独有的元素（当时是 v1 的「事件链」标签页
> 和旧的四家公司列表）。
>
> 已停用 v1 仓库的三个 workflow 并删除该 Worker，域名归属固定下来。

Worker（`worker/index.ts`）承担两件事：把 `/api/v1/*` 的静态快照透出去，
以及定制简报的三段式在线生成（意图解析 → 知识库+互联网检索 → 报告撰写），
后者需要 `KB_LLM_API_KEY` 与 `EXA_API_KEY` 作为 Worker secrets。

## 8 · 人工复核

三个复核节点，全部走 CLI，每次裁决都写进 `data/reviews.jsonl` 并在
「信源」页展示聚合结果。

```bash
python3 pipeline/review.py queue                      # 看待办队列
python3 pipeline/review.py event EV-xxxxxxxx watch    # 单个事件裁决
python3 pipeline/review.py batch pending watch --note "理由"   # 批量，只记一条
python3 pipeline/review.py merge EV-aaa EV-bbb split  # 归并纠错
python3 pipeline/review.py source latepost --class B  # 信源分级维护
```

复核状态具备粘性：`stage_verify` 每轮对全库重算，但已裁决过的事件
（`watching` / `confirmed` / `rejected` / `suspect_duplicate`）不会被重置回
`pending`。这条是踩过坑之后加的——早先每轮跑批都会把人工结论洗掉。

## 11 · 换一个行业

改两个 JSON——`config/<dataset>.json`（观察主体、领域、检索矩阵、关键词、窗口）
与 `config/sources.<dataset>.json`（信源注册表与通道），然后
`python3 -m pipeline.run --dataset <dataset>`。数据落 `data/<dataset>/`，
与主数据集完全隔离。

> **已实测一次**：`auto` 数据集（新能源汽车与智能驾驶，我方设为理想汽车）。
> 流水线代码一行未改，只新增两个 JSON。一轮跑下来采集 636 条 → 入库 170 条
> → 45 个事件、526 条断言、1 期周报，成本 Exa $0.154 + LLM ¥0.59。
> 顺带验证了两件事：信源表里的通用科技媒体可直接复用（16 个），只有垂类需要新增；
> 汽车垂类 RSS 的失效比例与电商一致（第一电动 / 盖世 / 汽车之家 / 车东西 /
> 42 号车库 / RSSHub 路由实测全部 HTTPError），说明「垂类订阅源不可靠、
> Exa 才是主力」不是电商的偶然。
>
> 这个数据集只做到「跑通并留下数据」，没有接入线上站点——线上仍只服务电商数据集。

提示词里的枚举全部从 config 读取，不必改代码。早先这些是硬编码的，
往 config 加主体不影响 LLM 阶段——这条是修过的坑，不是先见之明。

## 12 · 已知局限

诚实列出，不粉饰：

1. **A 类信源仍然稀薄。** 接入美团技术团队 RSS 后 A 类条目从 2 条涨到 20 条，
   「官方一手」这档从 0 个事件涨到 16 个；但「官方口径被第三方下修」至今只出现过
   1 次——A 类要起作用需要官方与第三方同时报道同一件事，这个重叠仍然稀少。
   完整的不足清单与改进方向见仓库根目录的 `交付说明.md`。
2. **RSSHub 公共实例不稳定。** 最近一轮 36 氪与新浪科技的全部实例超时，
   记入 `collect_errors` 但不阻断流水线。
3. **付费墙信源只能拿到标题与导语**，落库标记 `partial_content`。
4. **单源事件占比高。** 133 个事件里 117 个只有 1 个独立组织支撑，
   一律标「单源待确认」或「深度单源」并进复核队列，不隐藏。
5. **Exa 依赖度过高**（八成条目），检索服务的召回偏好会传导为覆盖偏差。
6. **未接入需登录的内容**，商家后台、内部群、付费社群一律不采。
7. **落地阶段依赖报道措辞。** 官方常把试点说成上线，交叉打折只在同一事件
   同时有 A 类与非 A 类信源时才生效——目前极少满足。

## 13 · 安全与合规边界

- 只采集**公开可访问**信息，遵守 robots.txt，不绕过登录墙与付费墙
- 正文只保留截断摘录与原文链接，不存储也不再分发第三方全文
- AIHOT 作为发现渠道接入：其公开使用规则对个人非商业与组织内部使用免费，
  本项目为内部审阅与个人使用、不对外分发。落库一律用原文链接，
  信源按原文发布方归属而非记为 AIHOT
- 竞对信息全部来自公开渠道，不涉及任何非公开信息获取
- 输出仅供内部研究参考，**不构成投资建议**
- 涉及我方业务的借鉴建议均标注「需内部数据验证」
